# RAG の概念

## RAG とは

**RAG (Retrieval-Augmented Generation, 検索拡張生成)** は、
「LLM に質問する前に、関連する資料を検索してプロンプトに添える」手法です。

```
普通の LLM:  質問 ────────────────────────▶ LLM ─▶ 回答 (学習データの知識だけで答える)
RAG:         質問 ─▶ 検索 ─▶ 関連資料 + 質問 ─▶ LLM ─▶ 回答 (資料を根拠に答える)
```

## なぜ必要か

LLM には次の弱点があります。

| 弱点 | 例 | RAG でどう解決するか |
|---|---|---|
| 非公開の情報を知らない | 自社の就業規則、社内 Wiki | 社内資料を検索して渡す |
| 知識が古い | 学習後に改定されたルール | 資料を差し替えるだけで最新化できる |
| もっともらしい嘘をつく (ハルシネーション) | 存在しない規程をでっち上げる | 「資料にないことは答えない」と指示し、出典を示させる |

「全部の資料をプロンプトに入れればいいのでは？」という疑問はもっともで、
資料が少なければそれが一番簡単で正確です (→ [設計判断](02_design_decisions.md#0-そもそも-rag-が必要か))。
資料が大量になると、コスト・速度・ノイズの面で「必要な部分だけ渡す」RAG が効いてきます。

## 2 つのフェーズ

### インデックス作成 (オフライン・事前に 1 回)

1. **読み込み (Load)**: 資料をテキストとして集める
2. **チャンク分割 (Chunk)**: 検索しやすい大きさに切る
3. **埋め込み (Embed)**: 各チャンクをベクトル (数値の配列) に変換する
4. **保存 (Store)**: ベクトルとチャンク本文をセットで保存する

### 質問応答 (オンライン・質問のたび)

1. **質問の埋め込み**: 質問も**同じ方法で**ベクトルに変換する
2. **検索 (Retrieve)**: 質問ベクトルに近いチャンクを top-k 件取り出す
3. **生成 (Generate)**: チャンクと質問をプロンプトに詰めて LLM に回答させる

## キーになる概念

### 埋め込み (Embedding) とベクトル

テキストを「意味の近いものほど近くに来る」ような座標に変換したもの。
こうすると「関連する文章を探す」ことが「近い点を探す」という計算の問題になります。

- **疎ベクトル (Sparse)**: TF-IDF や BM25。語彙数ぶんの次元があり、ほとんどが 0。
  出現する単語に基づくので、**キーワードの一致**に強く、**言い換え**に弱い
- **密ベクトル (Dense)**: ニューラルネットの埋め込みモデル。数百〜数千次元で全要素に値がある。
  **意味の近さ**に強く、型番や固有名詞の**完全一致**はやや苦手

このリポジトリでは `python tutorial.py` の STEP 3 で、実際のベクトルの中身を確認できます。

### コサイン類似度

2 つのベクトルの「向き」がどれだけ揃っているか (-1〜1)。
長さを 1 に正規化 (L2 正規化) しておけば、ただの内積で計算できます
(`rag/vector_store.py` の `self.vectors @ query_vector` の 1 行がそれです)。

### top-k と足切り

- **top-k**: 上位何件を LLM に渡すか。少ないと正解を取りこぼし、多いとノイズとコストが増える
- **min_score**: どのチャンクも似ていないときに、無関係な資料を渡さないための下限

### Retrieval と Generation は別々に評価する

回答が間違ったとき、原因は大きく 2 つに分かれます。

1. **検索の失敗**: 正解が書かれたチャンクを取ってこられなかった
2. **生成の失敗**: 正しいチャンクを渡したのに、LLM が読み違えた・無視した

実務の失敗の多くは 1 です。だからこそ `evaluate.py` で検索だけを切り出して測れるようにしています。
