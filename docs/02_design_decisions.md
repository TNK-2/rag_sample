# 技術選定と設計判断のポイント

RAG の設計は「正解が 1 つ」ではなく、データの量・種類、求める精度、運用コストのトレードオフです。
ここでは、このリポジトリで**何を選んだか・なぜか・本番ならどう考えるか**を整理します。

---

## 0. そもそも RAG が必要か

| 状況 | おすすめ |
|---|---|
| 資料が少ない (数十ページ程度) | **全部プロンプトに入れる**。検索ミスが起きず、一番正確。プロンプトキャッシュを使えば繰り返しのコストも下がる |
| 資料が多い / 頻繁に更新される | RAG |
| 「最新の Web 情報」が必要 | Web 検索ツールを LLM に持たせる |
| 口調や出力形式を変えたい | RAG ではなくプロンプト調整 (ファインチューニングは最後の手段) |

このサンプルの資料は小さいので、実は全部入れても動きます。RAG の仕組みを学ぶために、あえて検索を挟んでいます。

---

## 1. 言語・フレームワーク

**選択: Python + numpy だけで自作 (LangChain / LlamaIndex は使わない)**

- 学習目的では、フレームワークが隠している「チャンク → ベクトル → 内積 → top-k」を自分の目で見ることが一番の近道
- 自作部分は合計 200 行程度。RAG の中核は思ったより単純
- 本番では、ローダー (PDF 抽出など) やベクトル DB との連携をフレームワークに任せると楽。
  ただし抽象化が厚いと、精度が悪いときに「どこで何が起きているか」を追いにくくなる点に注意

---

## 2. チャンク分割

**選択: 段落単位で 300 文字を目安に詰める。overlap 50 文字。見出しは本文とくっつける**

| 判断ポイント | 考え方 |
|---|---|
| chunk_size | 小さい → 検索は鋭いが、文脈が切れる。大きい → 文脈は残るが、無関係な内容が混ざって検索がぼやける。日本語なら 200〜800 文字あたりから試す |
| overlap | 境界で文が切れて情報が失われるのを防ぐ。chunk_size の 10〜20% が目安 |
| 区切り位置 | 固定長で機械的に切るより、段落 → 文 → 文字 の順に自然な境界を優先する |
| 文脈の付与 | チャンク単体では「何の話か」が消えるので、文書タイトルを前置してから埋め込む (`Chunk.text_for_embedding`) |

`python evaluate.py --sweep` を実行すると、パラメータで検索精度が変わる様子が見られます。
例 (TF-IDF):

```
chunk_size  overlap  top_k   Hit@k    MRR
       100       20      1    0.79   0.79
       300       50      3    0.93   0.88
       600      100      3    1.00   0.95
```

このサンプルは資料が短く、1 つの文書がそのまま 1〜2 チャンクになるため、大きいチャンクが有利に出ています。
**資料の性質によって最適値は変わる**ので、「一般論」ではなく自分のデータで測るのが大事です。

---

## 3. 埋め込み (Embedding)

**選択: デフォルトは自作の TF-IDF (文字 2-gram)。オプションで多言語ニューラルモデル**

| 方式 | 強み | 弱み | 向いている場面 |
|---|---|---|---|
| TF-IDF / BM25 (疎) | 依存なし・高速・説明可能。型番・固有名詞・専門用語の完全一致に強い | 言い換え・同義語に弱い | 用語が統一された技術文書、型番検索 |
| ニューラル埋め込み (密) | 意味の近さを捉える。言い換えに強い | モデルが必要、重い、なぜヒットしたか説明しにくい | 自然文の質問、FAQ |
| ハイブリッド | 両方の長所 | 実装・チューニングが増える | 本番の多くはこれ |

**TF-IDF の弱点の実例**: `evaluate.py` の「本を買うのに会社はいくらまで出してくれる？」は、
資料の「書籍購入」と**共通する文字が 1 つもない**ため、TF-IDF では見つかりません。
このように「質問者の言葉」と「資料の言葉」がずれる問題 (語彙のミスマッチ) は、
ニューラル埋め込みやクエリ書き換え (演習参照) で改善できます。

### 日本語特有の注意点

- 日本語は単語の間にスペースがないため、英語用の単語分割がそのまま使えない
  - このサンプル: **文字 2-gram** (依存なしで意外と効く)
  - 本格的には: 形態素解析 (MeCab, Sudachi) で単語に分割する
- ニューラル埋め込みは**多言語対応モデル**を選ぶ (英語専用モデルは日本語で精度が大きく落ちる)
- 全角/半角の揺れは `unicodedata.normalize("NFKC", ...)` で吸収する

### モデルごとのお作法

`intfloat/multilingual-e5` 系は、質問に `query: `、資料に `passage: ` を付けないと精度が落ちます。
埋め込みモデルを変えるときは、モデルカードで入力形式を必ず確認しましょう。
また、**埋め込みモデルを変えたらインデックスは全部作り直し**です (ベクトル空間が別物になるため)。

---

## 4. ベクトルストア

**選択: numpy 配列でのメモリ上の全件探索 (起動のたびにインデックスを作り直す)**

| 規模 | 選択肢 |
|---|---|
| 〜数万チャンク | numpy の全件探索で十分 (このサンプル) |
| 永続化・更新・メタデータ絞り込みが欲しい | Chroma, SQLite + sqlite-vec, PostgreSQL + pgvector |
| 数百万チャンク以上 | FAISS / HNSW などの近似最近傍探索 (ANN)、Qdrant, Weaviate, Elasticsearch/OpenSearch など |

判断のポイント:
- **既存のデータベースに寄せられないか**: すでに PostgreSQL を使っているなら pgvector が運用的に楽
- **メタデータ絞り込み**: 「人事部の資料だけ」「2025 年以降だけ」などの条件検索が必要か
- **アクセス制御**: 閲覧権限のない資料が検索結果に出て LLM 経由で漏れないか (本番では超重要)
- **更新頻度**: 資料が変わったとき、差分だけ更新できるか

---

## 5. 検索パラメータ

**選択: top_k=3、min_score=0.05**

- top_k は評価で決める。Hit Rate@k は k を増やすほど上がるが、LLM に渡すノイズとコストも増える
- 最近の LLM は長い文脈にも強いので、「多めに取って LLM に選ばせる」のも現実的な選択肢
- さらに精度が欲しい場合は **リランキング**: 多めに (例: 20 件) 取ってから、
  より精密なモデル (Cross-Encoder や LLM) で並べ替えて上位だけ使う

---

## 6. 生成 (LLM とプロンプト)

**選択: Claude (Messages API)。資料を XML タグで囲み、出典番号を付けさせる**

プロンプト設計のポイント (`rag/generator.py`):
- **資料と質問を明確に分ける**: `<documents>` `<question>` のようにタグで囲む
- **根拠の範囲を限定する**: 「資料だけを根拠に」「分からなければ分からないと言う」
- **出典を示させる**: `[1]` のように番号を付けさせ、ユーザーが原文を確認できるようにする
- **資料の中の指示に従わせない**: 資料に悪意ある文章 (プロンプトインジェクション) が紛れ込む可能性がある。
  社外の文書や Web ページを扱う場合は特に注意

モデル選択の考え方:
- 回答品質を優先するなら上位モデル、大量の問い合わせを捌くなら軽量モデル。**評価セットで比べて決める**
- `RAG_MODEL` 環境変数で差し替えられるようにしてある

その他の設定:
- `fallbacks="default"`: モデルの安全性分類器がリクエストを断った場合に、サーバー側で別モデルに切り替えて回答させる設定 (beta)

---

## 7. 評価

**選択: 検索精度を Hit Rate@k と MRR で測る (`evaluate.py`)**

- **Hit Rate@k**: 上位 k 件に正解チャンクが含まれた割合
- **MRR (Mean Reciprocal Rank)**: 正解が 1 位なら 1、2 位なら 1/2、… の平均。順位の良さも見る

評価セットを作るときのコツ:
- 実際のユーザーの質問ログから作るのが理想
- **資料と違う言い回しの質問**を必ず混ぜる (言い換えに弱い方式の弱点が見えるように)
- **資料に答えがない質問**も入れ、「分かりません」と言えるかを生成側で確認する

生成の評価 (回答が正しいか・資料に忠実か) は、人手の確認や、LLM に採点させる方法 (LLM-as-a-judge) があります。

---

## 本番に向けて追加で考えること

- **データ取り込み**: PDF の表・画像、ヘッダー/フッターのノイズ除去
- **増分更新**: 資料が更新されたとき、該当チャンクだけ再インデックス
- **アクセス制御**: ユーザーの権限で検索結果をフィルタ
- **観測性**: どの質問でどのチャンクが使われたかをログに残し、失敗を分析できるようにする
- **コストとレイテンシ**: 埋め込みのバッチ化、プロンプトキャッシュ、ストリーミング応答
